# Rafiq (رفيق)

**Bilingual clinic reception, in Arabic and English.** Rafiq is a voice-first prototype for natural doctor-directory questions and patient-selected appointment booking, with a text option for easier testing.

This is a demonstration, not a hospital service: all patient, doctor, and appointment records are fictional; no real clinic is contacted and no real appointment is made. Please do not enter real medical or personal information.

Rafiq is a prototype name, not a clinic brand; it has not been checked for trademark or domain availability.

The app uses Gemini Live for bilingual speech and server-side reception functions backed by the synthetic SQLite directory and appointment store. See [current runtime, verification and rollback](docs/reception-replacement.md) for the active design; older implementation notes are labeled as historical below.

Start the current app with `npm run dev`, then open http://localhost:5173. Current checks: `npm test` and `npm run build`. The optional calling-number field simulates caller metadata; leave it blank to test spoken-number collection. Use fictional data only.

## About the prototype

A monitored web prototype for conversational English and Arabic doctor-directory questions and patient-selected appointment booking. The records are synthetic, the database is local, and there are no telephone calls or hospital integrations.

Documentation: [current design](docs/health-voice-agent-design.md), [decisions and lessons learned](docs/decision-log.md), and [architecture alternatives](docs/architecture-rethink.md).

## Run it locally

Prerequisites: Node.js/npm and a Gemini Developer API key with access to Gemini 3.8 Live and ephemeral Live tokens.

1. Install dependencies with `npm install`.
2. Copy `.env.example` to `.env` and add the key to `GEMINI_API_KEY`. Keep `.env` local; it is ignored by Git. Never paste the key into chat or browser code.
3. Start the Express server and Vite web app with `npm run dev`.
4. Open `http://localhost:5173`, choose **Start session**, then enable the microphone or use the text test box. A browser may ask for microphone permission.

The model is deliberately fixed to `gemini-3.8-live`. `GEMINI_VOICE` selects the single voice for both languages; the current demo uses Fenrir, while `.env.example` defaults to Kore. Neither is a verified Saudi-Arabic voice recommendation. Listen to Arabic and English output and get Arabic-speaker feedback before claiming naturalness.

The running app uses Gemini Live directly, with no second model or framework. Native replies are not sentence-matched before playback. Function validation, patient/guest consent and transactional slot checks remain enforced; factual speech and reception-only scope are prompt requirements, not guaranteed output filtering. Full-turn audio still buffers before playback. `GEMINI_VERIFIER_MODEL` is unused; legacy verifier utilities are diagnostic/test-only.

All replies, including the Arabic opening, are generated by the current Gemini Live session in its configured voice (currently Fenrir). There are no prerecorded clips or recording fallbacks. The opening briefly mentions مجمع عافية الطبي and asks how to help; phrasing and delivery may vary naturally. Failed media uses the normal bounded Live recovery path. Opening latency now includes generation. Listen during testing: transcripts cannot establish voice naturalness.

Appointment speech omits the current Riyadh year, including final readbacks. In December, it also omits the year for the immediately following January; other different-year dates state the year. Full ISO dates remain unchanged internally. A changed doctor/day/time inside a positive-sounding confirmation is a correction, not consent: cancel, check availability and request fresh confirmation. Arabic context smoke tests run with `npx tsx scripts/smoke-booking-context.ts` and `--correction=doctor`, `--correction=day` or `--correction=time`. They use actual Live API/audio with typed input and simulated playback, but all database writes are isolated in memory; synthetic transcript reports go under `docs/superpowers/booking-context-*.json`.

## Database boundary

Availability uses app-computed relative days/weeks/calendar-months, preserving leftover days instead of rounding. A Hijri request selects native Saudi Umm al-Qura labels for the same stored UTC slots; Gregorian dates remain available. The chosen calendar persists through booking, but final consent/success requires the actual calendar date and time, never only a relative duration. Test the current Live path with `npx tsx scripts/smoke-booking-context.ts --calendar` (isolated DB, actual Live API, typed input). It consumes API usage without changing demo bookings. Natural date wording is no longer matched against whole labels before playback.

The active Express reception runtime opens one persistent SQLite file at `data/reception.sqlite` (or `RECEPTION_DATABASE_PATH`) and owns the connection. Gemini never receives SQL, a database handle, or a database credential. A model function call such as `search_doctors` is handled by the browser SDK, which POSTs a strict, allowlisted request to an Express route. The route validates the request, calls a server-side service/repository using parameterized SQL, and returns only approved fields and localized text. The browser returns that result to the Live session as a function response. Routine intake and clarification functions provide conversation objectives (`speechIntent`), not lines for Gemini to recite; bilingual fallback text stays internal. These functions cannot add patient or directory information.

Intake acknowledges the chosen time briefly before asking for an ID, then supports guests without repeating that question. A complete mobile has 7–15 digits (optional leading `+`); invalid numbers return field-specific validation and a retry instruction, retaining the chosen slot and name. Natural contact corrections are not checked against stale doctor-list text. Heard availability survives an unrelated interruption; unplayed consent/readbacks do not count as approval. Arabic times use full words such as `الظهر` and `مساءً`; spoken numbers are unrestricted in delivery. The agent says `ما عندي هالمعلومة` / “I don't have that information” for missing facts, without guessing or using the formal spoken word `الدليل`. Broad doctor lists offer three examples and ask for a specialty; full generated audio still buffers before playback, so a provider pause remains possible. Failed output gets one contextual spoken repair attempt, not automatic retries of writes or a guarantee against provider failure.

Patient identity is not accepted from the ID alone: the returned name must finish playback before explicit self-identification verifies that profile. Doctor/availability selection precedes requesting ID; volunteered IDs with booking intent may be checked immediately. One tool-handler context owns booking progress. Preparation does not write an appointment. Final summary playback must complete, followed by a fresh explicit affirmation. Interrupted/failed summary audio retains the draft but cannot authorize booking; replay repeats the summary without re-preparing or committing. The server checks consent and availability within its transaction. Only a successful function result permits a success claim.

The long-lived Gemini key stays on Express. The app issues a single-use, short-lived Gemini token locked to the model, voice, instructions, transcriptions, and approved functions; the browser uses that token for its direct Live connection. The Live API tool calls themselves still go through the app's HTTP routes for data access.

## Developer-only diagnostics

The expandable **Test log** is available only while running the Vite development server with `npm run dev`. Production builds hide the panel and do not collect or store browser diagnostic events. In development, it helps inspect tool arguments/results, booking context, timings, and transcript/audio events; credentials and PCM audio are not recorded.

Live smoke runs can write transcript/diagnostic reports locally under `docs/superpowers/`; generated reports and audio are intentionally excluded from Git.

## Demo data and scripts

Synthetic patient IDs: `P-1001`, `P-1002`, `P-1003`, and `123` (`Test Patient` / `مريض تجريبي`). The seed includes 30 fictional doctors, 10 specialties, English/Arabic aliases, and future appointment slots. Never enter real patient information.

Useful conversation checks after connecting:

- Ask in Arabic for “خالد العتيبي” or in English for “Dr. Khalid Al-Otaibi”; both should resolve to the same directory record.
- Ask for “Faisal” without a specialty; the directory has two matching doctors, so the agent should ask which one you mean.
- Request a doctor or specialty that is not in the directory; the agent should say it cannot find a match instead of guessing.
- Ask about a date with no open times, then choose one of the alternatives the database returns. Claiming that an unavailable time is open must not change the result.
- Try a complete booking with `123` (Test Patient) or `P-1001`, wait for the patient name to be read back, choose one of the returned slots, and confirm clearly. Restart the server and check that the chosen slot remains booked. The active reception database persists bookings; the legacy reset script below does not reset it.
- Ask for a diagnosis or a doctor recommendation, or tell the agent to ignore the directory. It should stay with directory facts and appointment tasks.

- `npm test` — offline unit, route, database, and client tests; does not call Gemini.
- `npm run typecheck` — TypeScript checks.
- `npm run build` — production client build plus typecheck.
- `npm test -- tests/client/prototype-simplification.test.ts tests/client/live-session.test.ts` — current delivery/recovery and session integration tests; no provider calls.
- `npx tsx scripts/smoke-natural-dialogue.ts --selective-regression` — typed Arabic/English casual, hesitation, scope-redirect and closing test; reports verifier-call counts. `--booking-start-regression` and `--english-regression` also exercise directory and availability checks without committing bookings.
- `npx tsx scripts/smoke-completed-booking.ts` — actual Gemini Arabic guest booking, including the patient-ID choice and incomplete mobile repair; `--english` tests English and `--registered` tests an existing patient. Requires the API server on port 3001. All database writes use disposable memory, never the running demo database. Reports are saved under `docs/superpowers/completed-booking-*.json`. Input is text and playback completion is simulated, so these tests do not evaluate microphone recognition or voice naturalness.
- Add `--last-transcript` to replay the user's saved dental/booking/name-readback/phone-correction sequence. The clarified dental intent replaces “Nincs több”; new patient-ID answers are explicitly marked as inserted. The report is `docs/superpowers/last-transcript-replay.json`. It does not reproduce the original microphone audio.
- `--registered --latest-identity` tests «اي، هذا الملف حقي» with actual Live. `--registered --identity-recovery` tests replay without resetting the found record. `--registered --transliteration-regression` injects one observed bad doctor-name argument; it records a caller clarification if Gemini does not retry itself.
- `npx tsx scripts/smoke-booking-context.ts --identity-negative` tests Arabic uncertainty and English rejection with zero bookings. Without flags it tests an unknown doctor and unavailable time; `--correction=doctor`, `--correction=day`, and `--correction=time` test changed details after a prepared summary. All use disposable databases.
- `npm run reception:audio:generate` creates the cached Arabic and English caller WAV corpus under the ignored `output/reception-live/fixtures/` folder. It calls Gemini TTS only for missing fixtures; run `npm run reception:audio:generate -- --force` to regenerate all clips, or `npm run reception:audio:generate -- --force --language=en` to replace only English fixtures. Use `--language=ar` to target Arabic. Generation requires `GEMINI_API_KEY` and consumes TTS API usage. Free-tier limits may stop a batch; successfully generated clips stay cached, and rerunning resumes with missing clips.
- `npm run reception:audio:smoke` replays the Arabic corpus through the Live controller's microphone input. Use `npm run reception:audio:smoke -- --english` for English, or run `npx tsx scripts/smoke-reception.ts --audio [--english]` directly. The smoke uses one 16 kHz mono PCM16 caller turn per cached WAV, sends 100 ms frames plus a 1,500 ms silence tail to give Live's automatic turn detection time to close the caller turn, and keeps the microphone stream open between turns like the browser. It captures provider input captions and agent transcripts/audio, and checks the in-memory database for the first name, confirmed phone, accepted doctor and time. The partial phone turns must not write an appointment. It does not use the persistent demo database. Reports and recorded agent WAVs are written under ignored `output/reception-live/<timestamp>-.../`.
- The audio smoke needs `GEMINI_API_KEY` and makes Live API requests; fixture generation separately makes TTS requests. Repeated smoke runs reuse the cached caller WAVs and do not call TTS. These synthesized callers exercise the audio route but do not evaluate real microphone capture, Saudi-accent recognition, or human voice quality. Spoken wording is not sentence-matched; the saved database result is authoritative.
- `npm run db:reset` — legacy local-development reset for `data/health-voice-agent.sqlite` (or `DATABASE_PATH`): clears bookings and restores that legacy database's seeded slot availability. It does not reset active reception bookings in `data/reception.sqlite`.

Historical diagnostics, not tests of production speech enforcement: `smoke-year-rollover.ts` and `smoke-calendar-verification.ts` call a second text model directly and consume API usage. `smoke-output-verification.ts` expects a configured remote-verifier route; the standard running app no longer configures it, so that script receives an unavailable response. These scripts do not describe the production delivery-only behavior.

Verification results for this simplification are recorded in `docs/superpowers/plans/2026-10-02-prototype-simplification.md`.

The active reception SQLite file at `data/reception.sqlite` (or `RECEPTION_DATABASE_PATH`) is persistent across server restarts. Back it up before intentionally clearing reception demo data; the legacy `npm run db:reset` command does not affect it. The separate legacy database defaults to `data/health-voice-agent.sqlite` (or `DATABASE_PATH`). Keep `.env` separate; neither database reset removes credentials.

## Safety and known limits

- Directory, patient, and booking facts must come from the app functions. Database facts override a caller's conflicting claims; the caller supplies intent and preferences, not stored facts.
- The agent does not recommend a doctor, assess medical suitability, diagnose, triage, or provide treatment advice. It cannot use web search or model memory for doctor facts.
- Native replies use natural wording without general sentence matching. One narrow local booking-status check regenerates contradictory success/approval wording once. Grounding and scope still depend on the prompt and model; spoken mistakes remain possible.
- Gemini reports ownership and final approval through explicit semantic decisions. Application functions enforce found/delivered records, fresh turns, delivered summaries, available slots and atomic writes. They do not independently prove that Gemini interpreted the caller correctly.
- Keep demos monitored and use fictional records only. Native speech may still be wrong; the prototype does not provide production-grade assurance.
- Offline tests replace the external Live provider; current Live smoke scripts exercise typed conversations with generated audio and real function calls. Historical classifier scripts test the old second-model design only. None certifies microphone recognition, voice quality or production safety.
- Voice quality is an evaluation gate: the same voice is configured for Arabic and English, but Saudi Arabic naturalness must be judged by Arabic speakers. A desktop browser and microphone are required for audio testing; the typed path uses the same Live conversation/session.
