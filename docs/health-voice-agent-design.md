Replacement selection: [architecture alternatives and recommendation](../_bmad-output/architecture-alternatives/comparison.md) and its [target spine](../_bmad-output/architecture-alternatives/architecture-alternatives.md) refine the planned server action context into resource-centered drafts/offers/operations, with Gemini owning conversational order. ## Current architecture decision

Keep Gemini Live and the existing web app. Netlify serves the Vite frontend and exposes the Express reception API through a Netlify Function; the active receptionist uses Netlify Database (Postgres). Local development uses Netlify's Vite/CLI integration and local Postgres emulator. No LiveKit/Pipecat migration or second model is used. Legacy SQLite services and fixtures remain separate and are not the active booking store.

Patient audio/text → Gemini Live → browser application functions → `/api/*` → Netlify Function / Express reception service → Netlify Database → function result → Gemini Live audio/transcript → playback. The browser requests a short-lived Live token from the server; `GEMINI_API_KEY` remains server-side. Default sessions do not validate sentence wording, names or date labels before playback. Legacy checkers remain explicitly injectable for diagnostics/tests; the app does not enable them. `GEMINI_VERIFIER_MODEL` has no effect on normal sessions.

Booking/session state, offers, operations, appointments, slot occupancy, events, media, history and effects persist in Postgres. Transaction-scoped connections, row locking and uniqueness constraints preserve atomic writes, recovery and competing-slot behavior across function invocations and restarts. The browser tool handler still coordinates conversational progress; it is not the source of truth for saved bookings. The server persists drafts and confirmed results so a lost response can be reconciled by operation ID without another booking. The local emulator reproduces normal persistence paths; the competing-final-slot regression must also run against real PostgreSQL because the emulator has a known cross-client savepoint limitation.

Grounding, bilingual reception-only scope and complete spoken summaries are prompt requirements, not guarantees from a transcript checker. Native speech can contain inaccurate facts even though the transaction is correctly constrained. Keep the prototype monitored and fictional.

Audio still buffers a complete generated turn; this change is not a streaming-player rewrite. Previous warm doctor searches measured about 3–6 ms and slot reads about 5–8 ms; provider generation and buffering can dominate perceived latency. New structured browser logs record session/turn IDs, tool arguments/results, HTTP/tool durations, first-output-audio timing, generated/unplayed transcripts, playback/recovery and booking snapshots. Copy log exports those details; the panel expands each event. Storage is bounded to 500 events and 64 KB of details per event, with explicit oversized-detail truncation. Tokens and raw audio are excluded; collection failure cannot stop conversation.

Verification: 403 offline tests across 37 files and production build passed. Three real typed Live flows covered 26 Arabic/English caller turns, incomplete-number repair, unknown qualifications, pending-summary replay and cancellation/closing, with zero verifier requests and no booking commits. Details are recorded in the prototype simplification plan. Playback was simulated from generated audio; listening and microphone testing remain necessary.

## Goal

Build a small web prototype that feels like a warm, capable hospital receptionist. Patients can ask factual questions about doctors and book available appointments by speaking or typing. The prototype is for demonstrating the agent’s conversation quality and guardrails; it does not connect to a hospital or handle real patient data.

## Agreed product scope

- A simple web app, not a visual phone-call simulator.
- Voice input and spoken replies, live transcript, and optional text input for easier testing. Text and speech use the same conversation flow.
- The opening is Arabic-only: “السلام عليكم، أهلًا بك في مجمع عافية الطبي. كيف أقدر أساعدك؟” The clinic's English name is “Afiyah Medical Center.” Do not ask the caller to choose a language. Start in Arabic, switch to English when the caller clearly speaks English, and switch back when they clearly speak Arabic. Support no other conversation language. An isolated English doctor name or borrowed term inside an Arabic utterance does not trigger a language switch; for mixed or unclear speech, stay in the current language and ask a focused repair question.
- Arabic responses use polite, neutral Saudi Arabic. English responses use a warm, clear, professional receptionist style.
- A standalone “Hello”/“alo” is ambiguous with Arabic «ألو» and keeps the current language; clear English speech still switches to English. During an ongoing conversation, an attention greeting should check continuity and return to the known doctor/appointment question, not start reception again. Explicit Arabic «ألو» is recognized as Arabic locally. This mitigates noisy recognition without rewriting captions or pretending the original audio is known.
- Prefer natural caller questions that do not depend on gender. Do not infer caller gender from one uncertain «حاب/حابة» caption, voice, or name. Follow an explicit caller correction immediately; no gender question is needed for booking.
- Treat speech recognition as imperfect. Use audio and conversational context, and clarify only the uncertain detail without repeating nonsense or resetting the flow. Do not guess patient IDs, dates, phone numbers, or consent. For unsupported-language input, ask the caller to repeat in Arabic or English.
- The prototype does not disclose that the agent is AI, per the prototype requirement.
- Patient ID is requested only after booking intent, doctor selection and availability playback; the conversational guidance places the request after the caller chooses a time. Directory, doctor-detail, specialty, and read-only availability questions never trigger patient-ID intake or lookup. A patient may volunteer their ID with a booking request; otherwise the agent later asks whether they have one or want to continue without it. Registered profiles are looked up, the returned name is read back, and only a clear self-identification after playback verifies the profile; no OTP or external identity service is in scope.
- A caller without a patient record can book as a guest. After agreeing to a specific available appointment, they provide a full name and mobile number. The agent reads these details and the appointment back for final confirmation; the app creates a synthetic patient profile and booking only after that confirmation.
- Patients can ask about or search for doctors using facts present in the directory. The agent does not recommend doctors or infer which doctor is medically suitable.
- The agent helps book a doctor and time selected by the patient, subject to the stored schedule.
- The agent can close the conversation after completing the request, when the patient declines to book, or when the patient says they are done. The web app ends the voice session after the spoken closing and can offer a fresh session afterward.

## Prototype data

Use synthetic data only:

- 30 doctors across 10 specialties.
- Explicit English and Arabic doctor names, specialty names, and authored aliases, each tied to a stable canonical ID.
- Resolve Arabic or English doctor/specialty aliases to the same canonical record, but display the exact database name and specialty fields for the active conversation language (Arabic fields in Arabic; English fields in English). Never translate or transliterate those directory facts with the model.
- The approved doctor directory fields are name and aliases, specialty, clinic location, languages spoken, and appointment availability. Do not include biographies, credentials, ratings, or other facts unless they are explicitly added to the mock dataset.
- A small set of synthetic patient profiles keyed by mock patient ID.
- Guest profiles created from caller-provided names and mobile numbers only when their appointment is confirmed; their mock patient IDs are generated by the application.
- A seeded set of upcoming appointment slots with varied availability so the demo can show both successful and unavailable requests.
- Persistent appointments created during prototype use.

## Data grounding and guardrails

The agent’s factual claims about patients, doctors, specialties, locations, languages, and schedules must come from either the patient’s current input or a successful result from the prototype data store. The agent must not use general model knowledge or web search to fill in missing directory or patient facts.

All replies may use natural wording around the returned facts. Production output buffering checks media readiness, not sentence similarity or semantic truth. Interruption discards unfinished audio, not the chosen appointment. Functions remain the authority for permitted database actions.

The user approved removing the speech wording checks while retaining action safeguards. Instructions guide factual grounding and scope; they do not prove correctness of every spoken sentence.

Guest-only functions require the explicit guest path; an unresolved caller is redirected to the patient-ID choice after an available time has been selected. They must not silently assume that a caller is unregistered. Patient lookup preserves the offered times. The normal flow no longer requires separate initial guest-slot consent: choosing a time and requesting booking leads to ID choice, contact collection, preparation, then one final confirmation. The legacy confirm_guest_slot handler remains for old diagnostic fixtures but is no longer exposed to Gemini. Guest-contact numeric evidence can reject padded/invented preparation arguments, while incomplete function input returns a repair request. These checks govern action data, not natural spoken phrasing.

For the web prototype, the complete generated final summary appearing in the chat counts as presentation. A fresh unambiguous caller confirmation can commit while its audio is still playing; interruption does not force another full summary. This is tracked separately from completed audio playback in diagnostics (booking_summary_presented, summaryPresented). Withheld or unfinished output is not presented. Without a transcript presentation callback, full playback completion remains required. This is not proof the caller heard every word and is not a production telephone consent design.

Contact evidence is retained throughout guest intake, including digit-by-digit Arabic/English word sequences. A correction replaces the earlier number; it does not append digits. If asked to read a partial number back, the agent should answer with the digits it heard and then ask for completion. It must not describe incomplete supplied details as a number already saved in a patient record. This remains conversational guidance; the preparation-argument check is local and deterministic.

The Arabic opening is generated live through the same session and configured voice as subsequent replies (currently Fenrir). Keep the clinic name and brief help question, but allow natural phrasing rather than exact wording. There are no prerecorded clips or recording fallbacks. Failed opening media uses the normal bounded recovery path; provider disconnection still requires restarting. Live generation adds opening latency and variation; it does not guarantee consistent pronunciation. The user's report of robotic early replies and a more human fourth reply remains a listening observation, not an audio evaluation by automated tests.

The data store is authoritative for fixed records and availability. The patient is authoritative for current intent and preferences, such as which doctor and appointment time they want, and for guest details they provide directly. If the patient claims a stored doctor or slot fact is different, the agent explains what the directory or schedule currently shows and offers supported alternatives. It does not silently change doctor, specialty, or schedule records.

For a broad availability question, the server groups the stored 15-minute starts into up to three contiguous windows, factoring in service length, existing bookings, lead time, and Riyadh dates. The agent can tell the patient a date and a range of appointment start times, then ask which exact time they want. A range does not hold or reserve a slot; after the patient chooses, the server checks that exact start again and returns an offer for one clear agreement. This avoids presenting only the next 15-minute slot while preventing a broad window from being mistaken for a booking. Searches populate capacity lazily for the selected doctor over the 30-day horizon, so the shared demo database does not need bulk slot seeding.

Patient identity must not be inferred from the patient ID alone. The application permits patient lookup only after the explicit `begin_booking` transition. The localized database name must finish its spoken read-back first. Gemini interprets the caller through `confirm_patient_identity(decision: own_record | not_mine | unclear)`; caption phrase lists do not approve or reject ownership. The application requires a found, delivered record and a fresh completed caller turn. Unclear ownership preserves the lookup and appointment preference; rejection discards the unverified record; ownership permits draft preparation, never a database commit.

The agent may request searches through narrow, structured filters, such as a doctor name, canonical specialty, language, or location. Filters are optional: when a patient broadly asks what doctors are available or requests the doctor list, return a short database-backed sample and invite them to narrow by name or specialty. A separate directory function returns the stored specialty list. The application validates allowed fields and performs the lookup. The model cannot send raw SQL or arbitrary database commands. Arabic and English aliases resolve to canonical IDs in application logic. If a name maps to multiple doctors, the agent asks the patient to clarify; if no record matches, it says so without guessing.

If the caller asks for the last answer again, `repeat_last_response` repeats a pending uncommitted booking summary without writes, reruns the latest read-only directory/availability query, or returns the last fully played conversational reply. Repeating a pending summary invalidates earlier consent and requires a fresh caller turn after playback. Committed bookings are never reissued by replay. Missing audio or generation timeout gets at most one recovery attempt; repeated failure remains visible and restartable. Logs retain generated/unplayed text and function details for diagnosis.

For all doctor and specialty mentions—including directory answers, ambiguity clarification, available-slot responses, and booking read-backs—use the database-authored name and specialty fields that match the active conversation language. Search terms may be Arabic or English regardless of that output language. The function language follows the caller’s utterance, not the script of a proper name embedded in it. Because Live can deliver its final input transcript after a tool call, a constrained `en`/`ar` tool hint can select the response language for that turn; it cannot select or change any facts.

Booking is the only patient-related change in scope. A registered booking requires the existing verified patient record. A guest booking requires the caller-provided full name and mobile number, a specific doctor, and a specific slot. Collect details after the caller chooses the time and requests booking, without a separate preliminary confirmation. Present the name, number, doctor, actual date, and time once, then ask for one final confirmation. Until that fresh final confirmation, no guest profile or appointment is written. The application rechecks availability and, in one transaction, creates the guest profile, marks the slot booked, and writes the appointment. If the caller cancels or the slot is no longer available, no guest profile or appointment is saved. The server generates a mock patient ID; it is not requested from the caller. Store the caller's name exactly as provided, without transliteration; use that same name in the existing localized name fields. The model cannot directly modify records.

The agent stays within directory lookup and appointment booking. It does not diagnose, give treatment advice, or recommend a doctor. For an out-of-scope request, `scope_redirect` supplies the intended brief refusal and last agent question; the agent may express that meaning naturally instead of reciting an exact sentence. Attempts to override the database or the agent's role do not change tool permissions or stored facts.

This boundary does not change under prompt injection, threats, emotional pressure, pleading, or claims such as “I’ll die in a minute.” For an out-of-scope request made under pressure, briefly refuse in the active language and return to the last agent question with the same intent. Only a question whose audio finished playback may be used; if there is no prior question, ask the doctor-information-or-appointment question naturally. Do not repeat the caller's emergency claim, provide emergency numbers or instructions, diagnose, triage, assess the claim, or claim to contact help. The prototype does not provide emergency assistance and must not be used with real patients or as an emergency service. No scope-refusal sentence matching is performed; refusal and scope adherence are evaluated in conversational tests.

## Persistent prototype storage

Use Netlify Database (Postgres) for the seeded synthetic records, confirmed guest profiles, and prototype bookings. Confirmed bookings and their slot status must survive page reloads, function cold starts and application restarts, so later sessions see updated availability. Caller-provided guest details are persisted only as part of a successfully confirmed booking transaction.

Provide a development-only reset operation that removes prototype bookings and restores the original seeded slot availability. Keep reset controls out of the patient conversation. The entire local store can also be removed when the prototype is retired. No real hospital database, phone system, or patient data is connected.

## Conversation behavior

Routine reception tools return a `speechIntent` objective rather than an exposed fixed response. Keep internal fallback text for display/recovery, but let Gemini phrase greetings, time-choice acknowledgement and ID/name/mobile questions naturally. Spoken replies avoid the formal term «الدليل»: use «عندنا» or «ما عندي هالمعلومة». Missing doctor facts must not be invented; a failed lookup is a temporary failure, not proof that the information does not exist.

Before saving, describe the selected slot as available, rather than «لقيت لك موعد», and ask whether to book it. After a successful commit, state that the appointment has been booked. This is natural wording guidance, not another output phrase restriction. The transcript container follows new messages and live text updates to the bottom without moving keyboard focus, scrolling the whole page, or removing earlier bubbles.

Guest contact repair retains the heard appointment and caller-provided name. Mobile validation accepts 7–15 normalized digits with an optional leading plus and returns a field-specific, retryable error for incomplete input; do not pad digits, require a Saudi ten-digit format, or restart identity intake. Natural intake questions are guided by context, while functions enforce booking permissions. Final booking summary needs the actual date, caller details and fresh final consent. Clear repeated assent such as «إي إي صحيح» is accepted, but a changed doctor/date/time is not consent to the old draft. Avoid internal caller labels such as «كضيف»; say that booking can continue without a patient ID. Prefer natural recipient-directed service wording such as «نحجز لك» and «نشوف لك» without enforcing fixed sentences.

Arabic authored times expand abbreviated periods into full spoken words, including «الظهر» at noon. The agent may pronounce digits as words; dates and time periods are authored from the actual stored slot. Broad doctor responses name three samples instead of five; database lookup is small, but full-turn native audio buffering remains a latency source. Interruptions do not add false error bubbles or discard heard availability. Failed generated output gets one bounded contextual recovery attempt; uncommitted summaries and already-obtained guest agreement survive media interruption; no write is silently retried and repeated/provider failure can still require another caller turn or a restarted session.

English and Arabic wording is guided by the main prompt without a vocabulary allowlist or second model. Read-only lookup facts and caller intent stay in the Live conversation; booking permissions and saved facts belong to the server. Legacy transcript verifiers are test/diagnostic-only. The active browser does not run a transcript fact-checker or a local booking-status speech filter, so a spoken claim can still be inaccurate even though it cannot create an unauthorized database write. This reduces false withholding and latency, but leaves spoken accuracy dependent on the prompt and model.

The active consent path uses `accept_offer` for a specific available appointment and `commit_request(operationId)` for a ready operation. The server requires the offer and relevant patient/contact details, validates the accepted decision and current capacity, then writes the appointment and related effects atomically. Only `committed` confirms a saved change; retrying the same operation ID recovers its result rather than creating a duplicate. The semantic decision is interpreted by Gemini and can still be wrong; the server guards database effects, not the meaning of every spoken reply.

Historical decision, superseded on 2 October 2026: the app previously used `gemini-3.1-flash-lite` for meaning-based verification after lexical checks rejected harmless questions. It introduced provider/quota failure modes and extra latency. The main voice model remained `gemini-3.8-live`. Legacy classifier setup references: https://ai.google.dev/gemini-api/docs/generate-content/structured-output and https://ai.google.dev/gemini-api/docs/thinking. This configuration is no longer the running app's architecture.

Legacy local and semantic checker utilities are diagnostic-only. The runtime neither routes speech through a risk classifier nor matches supplied appointment labels. Identity/final-summary delivery and fresh consent are tracked independently of sentence matching.

Spoken appointment dates omit the current Riyadh year in availability, consent and final booking readbacks alike. In December, the immediately following January also omits its year (December 2026 → January 2027). Other different-year dates explicitly state it, including February next year or January two years later. A shared Gregorian/Riyadh formatter controls authored speech using the server's current date; full UTC timestamps retain the year internally. The prompt uses the supplied formatted labels instead of calculating the year convention itself. The rollover exception applies in both Arabic and English; it does not change appointment identity or consent requirements.

Availability defaults to app-computed relative wording: today/tomorrow, days, weeks plus remaining days, or Gregorian calendar months plus remaining days. Civil-day differences are calculated in Asia/Riyadh; a month is not approximated as 30 days. Month anniversaries clamp to the destination month's last day. All labels retain the appointment's exact time. `get_available_slots` accepts `dateStyle: relative | gregorian | hijri`; Hijri uses the explicit Saudi Umm al-Qura convention, not a guessed model conversion. Slot results pair relative, Gregorian and Hijri labels for the same stored UTC instant. Calendar changes do not select a new slot. The requested absolute calendar preference is retained by the application and included in booking preparation; pending server state retains it for success readbacks. Preparation/success responses include only absolute calendar equivalents, not relative labels, and final consent requires the actual date/time. Complete absolute final readback remains a prompt requirement; speech is no longer matched against these labels. No general Hijri-input-date parser is promised.

The interaction should feel concise and attentive rather than scripted. Keep one consistent voice and style: calm, warm, direct Saudi Arabic with natural intonation and small pauses; clear pronunciation for doctor names and appointment times; professional without sounding stiff or overfamiliar. Follow clear Arabic/English switches; keep the current language for mixed or ambiguous turns. Short, ordinary confirmations such as “sounds good” or “ماشي احجزه” should not unexpectedly switch away from the caller’s language.

3. For directory questions, search only approved stored fields and answer from returned records.
4. 5. For booking, clarify the requested doctor and date or time as needed, check stored availability, and offer exact available choices.
6. For a registered patient, follow the existing verified-ID and appointment read-back flow. For a guest, after they agree to the selected slot, collect only their full name and mobile number, then read back those details together with the doctor, date, and time and ask for final confirmation.
7. On final confirmation, recheck availability and persist the appointment; on the guest path, create the synthetic patient profile in the same transaction. Report success only after the write succeeds. If the caller declines or asks to end at any point, acknowledge that and close without booking.

Ask one useful question at a time. Keep replies brief, vary acknowledgements naturally, and avoid repeating information the patient already provided. The patient can interrupt spoken replies. For unclear input, ask about the specific uncertain detail rather than restarting the entire conversation. After repeated failures to understand, close politely and let the patient start a new session; do not guess or claim a human handoff exists.

## Demo and guardrail scenarios

The seeded data and scripted test conversations should cover:

- A complete English booking and a complete Arabic booking using Arabic doctor or specialty aliases.
- The Arabic-only opening with the clinic name, automatic Arabic-to-English and English-to-Arabic switches, short natural confirmation phrases that switch language correctly, English names inside Arabic speech without switching, and a repair for unsupported-language input.
- A guest booking in English and Arabic, collecting full name and mobile only after the caller agrees to a specific slot, then confirming all details before any database write.
- A directory or availability inquiry that never requests or looks up patient ID; an initial/repeated booking request that asks about the doctor rather than ID; an ID question deferred until availability has been heard; an already-provided booking ID checked without asking twice; and a no-ID choice that survives repeated booking requests.
- A guest who changes their details, declines final confirmation, or encounters an unavailable slot; no abandoned guest profile or appointment remains.
- A factual doctor lookup, including clinic location, spoken languages, or specialty.
- Varied everyday wording for doctor lists and specialties in both languages; broad requests return a short sample and ask how the patient wants to narrow it.
- Two similar doctor names that require clarification, plus an unknown doctor or specialty that returns no match.
- A patient claiming a doctor is available at a time that the data store marks unavailable.
- An unavailable requested slot followed by a booking of an offered available slot.
- Invalid or unclear patient ID, unclear speech, correction of a misheard name or time, and repeated no-match recovery. Include “yes/okay/sounds good” and Saudi “ايه/تمام/ماشي” confirmation variants, while refusing conditional or hesitant replies as consent.
- Microphone onset missed by local voice detection, and an input transcript that arrives after a tool call; retain the finalized utterance and do not reset or misattribute the current reply.
- A missing-audio or timed-out response gets at most one automatic recovery attempt. Pending summaries can be replayed without re-preparation or writes.
- A patient who declines to book or asks to end the session.
- Requests for diagnosis or doctor recommendations, and instructions to ignore the database or invent facts; the agent stays within its scope and uses only supported data.
- Persistence: after a confirmed booking, refresh or restart the app and verify the same slot remains booked; use the development reset to restore seed availability.

## Acceptance criteria

- Both voice and text can complete the same lookup and booking flows; speech input is transcribed and agent replies are spoken and shown in the transcript.
- Natural Arabic/English paraphrases, including spoken number words, are not blocked by sentence checks. Replay is read-only. Media failures cannot create an unbounded retry loop; an unplayed final summary cannot authorize a booking.
- Completed patient and assistant bubbles remain in the session transcript as later turns arrive; interim speech may update only the current unfinished patient turn.
- After a patient challenges a returned identity, the agent gives the fixed identity-denial reply at most once for that profile read-back; later turns are handled as new requests unless a new profile is looked up and read back.
- Arabic and English doctor/specialty names and aliases resolve to the intended canonical records; ambiguous matches trigger a clarification.
- No doctor, specialty, patient, clinic, or availability fact is asserted unless supported by the mock data or the patient’s current input.
- A registered booking cannot be recorded without a verified patient ID. A guest booking cannot be recorded without caller-provided name and mobile, a currently available slot, and explicit final confirmation of the complete read-back.
- A guest profile and its appointment are created atomically only after final confirmation; canceling or failing the availability recheck leaves neither behind.
- Confirmed bookings remain after page reload and application restart; reset restores the seeded demo state.
- The agent does not recommend doctors or provide diagnosis or treatment advice, and it closes gracefully when the patient is done.
- Arabic and English voice samples are reviewed for clarity and naturalness; the specific Saudi Arabic phrasing and voice quality need listening feedback from Arabic speakers.
- Gemini Live receives `ar-SA` and `en-US` transcription hints, which are hints rather than a hard input-language allowlist. Enforce the two-language conversation/output policy in the agent instructions and repair flow. Live input transcriptions may be delivered independently of tool events; verify actual recognition behavior with live Arabic and English audio before relying on it.

## Current conversation refinements

Current component/function/database connections are shown in [the implementation architecture diagram](implementation-architecture.html). It groups browser modules, Gemini Live, the Netlify Function and Postgres database, and distinguishes native voice processing from app-owned booking state.

- Arabic should remain professional Saudi speech with the same voice identity, pace and pronunciation within a reply and across replies. Avoid broad social questions such as «وش في بالك اليوم؟»; follow the caller's reception request. These are delivery guidelines, not scripted lines or guarantees of accent consistency.
- Introduce a doctor with the database's full localized name once. Later references can use the title and first name when unambiguous; use the full name in final appointment readback/confirmation and when distinguishing shared first names. Function identifiers stay canonical.
- Identity replies such as «اي صحيح» and «نعم، صحيح» can express ownership after the returned patient's name has been delivered. Gemini reports the meaning explicitly, rather than the app recognizing a growing list of captions. Denial, conflicting names and related-person statements are guided to rejection/clarification; identity acceptance never substitutes for fresh final appointment approval.
- When ownership confirmation is unclear, preserve the found patient record and selected doctor/time. Return needs_identity_confirmation and clarify ownership only; do not report an invalid ID or restart ID collection. Replay repeats the pending identity question. Explicit contradictions still discard the record, and uncertain replies never authorize a booking.
- Test realistic caller wording and microphone transcript/tool ordering, not only typed happy paths. The latest loop regression and rationale are in the decision log. Text-based Live tests cannot establish microphone ASR accuracy or perceptual voice quality.
