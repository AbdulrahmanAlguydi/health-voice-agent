Current implementation · Architecture · Afiyah Medical Center

One voice model. App-controlled booking.

Gemini handles the Arabic/English conversation and requests functions. The browser executes those requests through the application; the server reads and writes the database. Gemini never connects to SQLite directly.

Real functions—not direct database access

Read stored facts
list_specialties · search_doctors · get_doctor_details
get_available_slots · lookup_patient
Progress through booking
begin_booking · confirm_patient_identity
prepare_booking · prepare_guest_booking
confirm_booking · cancel_pending_booking
Recover or close the conversation
repeat_last_response · speak_safe_reply · end_session

The handler returns data to the session controller, which sends function results back to Gemini. Some functions change browser state only; database-backed functions use the API.

Who decides what?

Separate conversation from permission to save

Gemini: understands doctor/time preferences, reports identity ownership and final approval, and speaks naturally.

Browser app: checks valid progress, fresh caller turns, delivered identity/summary, contact digits and duplicate confirmation.

Server + SQLite: resolve stored aliases, validate records and availability, and commit the appointment in a transaction.

Setup: the browser requests a short-lived Live token from the server; the server obtains it from Google using the configured API key. That setup exchange is omitted from the arrows above.

Current limits: no second verifier model, separate STT/TTS services, prerecorded lines, LiveKit, real telephone network or hospital integration. Semantic decisions and ordinary spoken facts still depend on Gemini's interpretation; the local status check is narrow, not a guarantee against every mistake.

Debugging: browser diagnostics capture transcripts, functions, API timing, booking state and withheld output; the UI provides logs/export for testing. Logging is cross-cutting, so it is described here instead of adding another box.
