Current implementation · Architecture · Rafiq (رفيق)

One voice model. App-controlled booking.

Gemini handles the Arabic/English conversation and requests functions. The browser sends structured requests through the Netlify Function; the Express API reads and writes Netlify Postgres. Gemini never connects to the database directly.

clinic_information · find_available_slots
find_my_appointments · select_appointment
Capture details + act on an offer
set_booking_details · capture_contact
confirm_contact · accept_offer · commit_request
Recover, follow up or close
get_operation · record_followup
set_emergency · end_session

The browser sends Gemini's structured function requests to the API and returns the server result to the Live session. Reception state and database facts are owned by the server.

Who decides what?

Separate conversation from permission to save

Gemini: understands doctor/time preferences, interprets caller decisions and speaks naturally.

Browser: streams voice/transcripts and carries typed function requests; it does not own persisted booking state.

Netlify Function + Postgres: validate caller progress, identity and available records, then commit booking effects atomically.

Token setup: the browser requests a short-lived Live token from the server; the server uses the configured API key. That setup exchange is omitted from the arrows above.

Current limits: no second verifier model, separate STT/TTS services, prerecorded lines, LiveKit, real telephone network or hospital integration. Semantic decisions and ordinary spoken facts still depend on Gemini's interpretation; server-side write checks do not verify every spoken claim.

Debugging: browser diagnostics capture transcripts, functions, API timing, booking state and withheld output; the UI provides logs/export for testing. Logging is cross-cutting, so it is described here instead of adding another box.
