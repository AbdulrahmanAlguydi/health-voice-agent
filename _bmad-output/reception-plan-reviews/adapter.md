# Adapter plan review

Reviewed 3 October 2026 against `reception-contracts.md`, `plan-reception-replacement.md`, the alternatives spine, and the existing App/session/audio/Transcript interfaces. Read-only runtime review; no runtime changes.

Verdict: architecture is implementable without another provider or framework. Resolve the following contract details before dividing implementation ownership. These are routine technical corrections, not new product choices.

## Required corrections

1. **Order presentation against the caller's input, not just offer issuance.** Commands and media events have opaque `eventId` values and `inputSequence`, but no common event order. A caller can start saying yes before playback starts, while the eventual acceptance command arrives afterward; `inputSequence > issuedInputSequence` alone would accept that yes. Add monotonically increasing session `eventSequence` to commands/media events, and immutable `inputStartedEventSequence` to command context. Persist the first presentation event sequence for each output/offer. Validate that the accepting caller turn began after presentation started. Keep uncertain/interrupted presentation contextual, without requiring completion or captions. IDs remain adapter supplied; canonical event fingerprints and connection generations reject altered replay/stale events. Sequence ordering must survive reconnect rather than restart at one.

2. **Distinguish actual audio exposure, text presentation, and received output.** Add `medium: 'audio' | 'text'` to media events and define `started` as actual audio-source start (or committed text presentation), never PCM arrival or transcript callback invocation. Muted/skipped audio must not emit audio-started/completed evidence. Preserve separate media records for one output instead of overwriting audio evidence with text evidence. Offer IDs attach to a specific future assistant output after the availability tool result; issuing that result is not presentation. The adapter's association is exposure metadata, not an assertion that exact details were spoken. Semantic `detailsCommunicated` remains a separate model argument. Flush the serial media-event queue before an acceptance command; require server acknowledgement before relying on the event. A failed flush produces an unresolved/clarification result, not fabricated exposure.

3. **Separate goodbye intent from irreversible domain closure.** `end_session` currently promises both an immediate admission fence and cancellation by new speech "before domain end". Once the tool closes the server session, cancelling a pending browser close cannot restore it. Use a two-phase conversational end: the model function records a pending end intent and its output/input identifiers; actual farewell playback drain (or explicit text-only presentation completion) invokes an adapter finalize-end event that atomically fences/closes the session. New caller input before finalization cancels pending intent. Explicit UI End can fence immediately. Define timeout/playback-failure/disconnect behavior so end intent remains visible as unresolved instead of waiting indefinitely or falsely reporting completion. GenerationComplete/turnComplete alone are insufficient to prove playback drained. Do not silently reopen a finalized closed session.

4. **Fix neutral UI/media types before parallel integration.** The plan names new streaming callbacks/player methods but leaves signatures unspecified. Existing `SessionControllerCallbacks.onApprovedOutput` takes a complete `ApprovedOutput`; `App.tsx` and `Transcript.tsx` import that legacy gate type. `PcmAudioPlayer.play()` stops previous audio on every invocation, so it cannot receive one chunk at a time. Specify a gate-free `RecordedOutput` and callbacks keyed by `outputId`, plus `beginStream`, `enqueue`, `endStream`, and actual start/drain/error callbacks. Retain `play(recordedOutput)` for replay only. App attaches text/replay data by output ID, replacing the single `pendingAssistantMessageId` assumption. Expose stable session API/types from a neutral module so the replacement does not import the old controller just for public interfaces. Keep old fixtures explicitly legacy and adapt token fixtures rather than mixing live permission sets.

## Turn-attribution implementation requirement

The installed provider SDK explicitly documents that input/output transcriptions have no guaranteed ordering relative to model turns (`node_modules/@google/genai/dist/genai.d.ts`, LiveServerContent); Transcription has no turn ID. Therefore final ASR must not create a new consent turn or overwrite the newest input turn's identity. Allocate typed and microphone-activity input IDs independently of captions, retain immutable input records, freeze command carriers at dispatch, and mark ambiguous microphone/tool attribution uncertain. A later local VAD onset does not prove that a delayed tool call was produced by that newer input; use a response epoch and uncertainty when overlapping activity prevents confident association. Provider activity events supplement this only when emitted by the selected model. Do not assume allowlisted VAD signals or untested manual activity detection. This limitation is compatible with the prototype convention but must be stated and tested, not disguised as exact provider correlation.

## Minimum acceptance sequences

- PCM before output caption; final caption after generation completes; replay attaches to the same output and invokes no API command.
- Tool before final ASR; late prior ASR after new VAD input; delayed prior tool after new input. No fabricated subsequent acceptance turn.
- Offer issued but no presentation; yes starts before playback; interrupted started output; muted text presentation. Assert distinct exposure evidence and correct acceptance outcome.
- Reconnect with an old media response still pending; deduplicated replay and strictly ordered event sequence; stale output cannot resume queued playback.
- Farewell queued then caller speaks; finalization races commit; explicit End; playback failure. Assert admission fence ordering and preservation of saved results.
- Streaming completion occurs only after the stream ends and every queued source drains; interruption stops every scheduled source without firing completed exposure.

No substantive user ambiguity remains after adopting these corrections. Continue implementation after updating the shared contracts and plan so server and adapter workers use the same lifecycle/signatures.
